# Concurrency scenarios, 2026-10-11 round

The two behavioral rules in [`../../global-rules.md`](../../global-rules.md) — capacity-limited
fan-out and concurrency refusal — run against the harness in [`../README.md`](../README.md): a
runtime with a hard cap, refusals while it is full, completion reported only through a blocking
`wait`, and every call written to a trace.

## Method

- Twelve samples: two scenarios, two model families (`gpt-6-luna`, `deepseek-flash`), three samples
  each. Every sample is a fresh runtime and a fresh agent, given the same brief (`runs/TASK.md` in
  each run directory) with the rule text quoted verbatim.
- Scenario A: 14 units, cap 10, nothing running, all units owned.
- Scenario B: 14 units, cap 10, the first ten already running, the caller owns `u11`-`u14`.
- Graded by [`../grade.py`](../grade.py) on eight criteria read from the trace, the runtime state
  and the caller's work list. The grader is itself tested: a scripted correct trace scores 8/8 and a
  scripted tight-retry trace scores 1/8.

Every sample met the scenario's precondition of at least one real refusal, so both rules were
actually exercised rather than described.

**The one failure is real.** B/luna-2 kept its work list correctly through the whole run — the trace
shows the refused units in `pending` and `refused` before each dispatch — but its final write left
`plan.json` as `...\"refused\":[]}}` with a stray brace, so the file is invalid JSON and nothing can
re-read it. The failure is the criterion about the work list; the other seven pass.

## What the traces show

- **Nobody slept, polled or retried.** All twelve traces contain only `status`, `start` and `wait`
  calls; no run of consecutive status calls, no unit refused twice, no call that ignored a full
  runtime. Waiting for completions happened inside the runtime's own `wait`.
- **Two dispatch styles, both correct.** The deepseek samples mostly fill to the cap and probe every
  remaining unit once (four refusals), while the luna samples more often start one unit, see the
  refusal, and switch to waiting (one refusal). In scenario A the same split appears: one luna
  sample turned a single refusal into a wait, the others probed all four.
- **The work list carried the state across the wait.** In every sample the refused units were still
  listed in `pending` or `refused` when capacity freed, and the next dispatch re-read that file
  rather than re-deriving the set.
- **Waiting cost real time.** In scenario B the preloaded units finish 60 seconds after the reset,
  so the samples that waited on `wait` picked up events only after one or more 20-second timeouts.
  No sample gave up or fell back to a fixed sleep.

## Defects found and fixed in this harness

1. **The re-readable criterion read the wrong evidence.** It first checked the caller's final work
   list, where a refused unit has already been dispatched and therefore no longer appears as refused
   — a false failure. The runtime now snapshots the caller's list on every call, so the criterion
   asks the real question: was the unit re-readable at or before the dispatch it was refused for.
2. **The continuation criterion punished correct behaviour.** It first required a dispatch to be
   immediately adjacent to an event, but one completion can free several slots, so back-to-back
   dispatch is right. It now reconstructs capacity from the trace and only fails a dispatch that
   ignored a full runtime.
3. **One defect was counted twice.** A work list that cannot be parsed made both the re-readable
   criterion and the work-list criterion fail. The first now judges only from the trace snapshots,
   and the second reports that the file itself is unreadable.

An earlier first pass used a 25-second preload window. Model latency exceeded it in two of six
scenario-B samples, so those subjects arrived after the preloaded units had finished, met no
refusal, and never ran the scenario; they scored 8/8 while testing nothing. The cell was rebuilt
with a 60-second window and re-run (archived under `runs/first-pass-25s/` in the working copy, not
committed). The window, not the subject, was the defect.

## Limits

- One model tier per family, three samples per cell. This is a behavior check, not a rate.
- The harness simulates the cap and the completion events; it does not exercise the real dispatcher.
  Real fan-out tools report completion through their own notices, which this trace cannot observe.
- A fixed sleep is invisible in a call trace: model latency and a deliberate pause look the same.
  The criteria therefore judge waiting indirectly — capacity is only freed by the runtime's event,
  and no trace shows a status loop or a repeated refusal.
- These are scripted single-task scenarios, not long-horizon work where a pending set must survive
  many turns.
